# S3.1: Balancer State And Controls

**Status**: DONE
**Wave**: W3
**Track**: UI foundation
**Supports**: D4
**Effort**: L
**Dependencies**: W1, S2.3

## Purpose

Build the mechanics control state model and first set of HUD-kit-based sliders/inputs for biomass, resource, and troop tuning.

## Scope

- In: Pending mechanics state, active mechanics snapshot, sliders/number inputs for first parameter set, dirty/valid state, HUD UI catalog primitives for surfaces/forms/controls.
- Out: JSON import/export, run lifecycle controls, live mutation.

## Touchpoints

- Create: `src/client/sandbox/SandboxBalancer.ts` or child components under `src/client/sandbox/`.
- Modify: `src/client/hud/ui/HudComponents.ts` and `src/client/hud/ui/HudCatalog.ts` only if a genuinely reusable missing primitive is needed.

## Acceptance Criteria

- [x] Controls cover the planned biomass/resource/troop parameter set.
- [x] Controls use existing HUD primitives such as `hud-surface`, `hud-surface-header`, `hud-surface-body`, `hud-form-row`, `hud-field-label`, `hud-input`, `hud-range`, `hud-select`, `hud-segmented-control`, `hud-button`, and `hud-pill` where applicable.
- [x] Pending and active values are represented separately.
- [x] Pending values do not mutate the active run.
- [x] If running-state edits are complex, controls become editable only while paused/not running.
- [x] One-off sandbox CSS is limited to layout glue that cannot be expressed with existing HUD primitives.

## Test Plan

- New sandbox component test - controls update pending state.
- New sandbox component test - active state remains unchanged until restart/apply.
- HUD catalog smoke test if a new reusable primitive is added.
