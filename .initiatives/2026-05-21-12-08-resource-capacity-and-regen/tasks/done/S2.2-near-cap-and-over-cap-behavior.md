# S2.2: Near Cap And Over Cap Behavior

**Status**: DONE
**Wave**: W2
**Track**: Cap correctness
**Supports**: D3
**Effort**: Medium
**Dependencies**: S2.1
**Hardened**: 2026-05-21

## Purpose

Verify passive resource regen respects capacity when stockpiles are near, at, or above capacity.

## Scope
- In: Per-resource cap clamping during passive income.
- Out: Capping trade/conquest/train/donation rewards.

## Context and Rationale
- Why this exists: Formula tests prove the helpers work; integration tests must prove the live tick does not overfill resource storage.
- Constraints: Reward paths other than passive regen remain uncapped by plan.
- Chosen approach: Seed player resources near and over capacity, execute `PlayerExecution`, and assert passive regen respects per-resource capacity.

## Behavior and Requirements
### B1: Near-cap clamping
- Given: a player has resources close to capacity.
- When: passive regen ticks.
- Then: each resource ends at or below capacity.

### B2: Over-cap stability
- Given: a player has resources above capacity due to non-passive paths.
- When: passive regen ticks.
- Then: passive regen does not increase those resources further.

### B3: Per-resource independence
- Given: different resources have different remaining headroom.
- When: passive regen ticks.
- Then: the clamped delta respects each resource independently.

## Touchpoints
- Create: None expected.
- Modify: `tests/core/executions/PlayerExecution.test.ts`, possibly `src/core/game/Resources.ts` if helper gaps appear.

## Acceptance Criteria
- [x] Passive regen clamps each resource to capacity.
- [x] At-cap resources receive no passive delta.
- [x] Over-cap resources remain stable and do not grow further from passive regen.
- [x] Clamping is per resource, not based on a scalar aggregate.
- [x] Tests do not imply trade/conquest/train/donation rewards are capped.
