# S1.2: Player Resource API

**Status**: DONE
**Wave**: W1
**Track**: Core model
**Supports**: D1
**Effort**: Medium
**Dependencies**: S1.1

## Purpose

Add resource stockpiles and mutation APIs to the player contract while preserving existing gold-facing behavior.

This ticket intentionally keeps resources in lockstep with compatibility gold. `addResources()` and `removeResources()` should accept the new payload shape, but the first implementation should reject or avoid non-uniform resource deltas because existing AI/UI/build affordability still reads `gold()`.

## Scope
- In: `resources()`, `addResources()`, `removeResources()`, `canAffordResources()`, starting resource initialization, compatibility `addGold()` / `removeGold()` behavior.
- In: Internal lockstep behavior between `_gold` and resource stockpiles for equal payloads.
- Out: Migrating all acquisition call sites; client update serialization; support for divergent resource balances.

## Touchpoints
- Create: None expected.
- Modify: `src/core/game/Game.ts`, `src/core/game/PlayerImpl.ts`.

## Acceptance Criteria
- [x] Player resource stockpiles initialize from the same starting economic value as current gold.
- [x] `addResources()` increments Food, Energy, and Materials according to the payload.
- [x] `removeResources()` removes a payload without underflowing stockpiles.
- [x] `canAffordResources()` checks all three resource balances.
- [x] Existing `addGold()` and `removeGold()` remain usable as compatibility wrappers.
- [x] `gold()` remains stable enough for current AI/UI/cost checks during this phase.
- [x] Non-uniform resource payload behavior is explicitly guarded or documented as unsupported for this compatibility phase.

## Test Plan
- `player initializes resources from starting gold` - verifies all three resources equal initial compatibility amount.
- `player addResources updates stockpile` - verifies payload mutation.
- `player removeResources clamps or removes consistently` - verifies spend semantics.
- `player canAffordResources checks each resource` - verifies affordability is not based on one scalar.
- `gold compatibility wrappers preserve old behavior` - verifies existing gold callers still work.
