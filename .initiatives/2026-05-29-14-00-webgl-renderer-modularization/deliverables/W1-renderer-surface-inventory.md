# W1 Renderer Surface Inventory

## Summary

The live game uses the custom WebGL2 renderer under `src/client/render/gl`.
The current public facade is `src/client/render/gl/GameView.ts`, which wraps
`GPURenderer` and `Camera` and exposes both reusable base-map operations and
OpenFront-only feature operations.

For Batch 1, the reusable Foundation path should be a thin adapter over the
custom WebGL path. It should share base visuals with OpenFront where the games
overlap: terrain, ownership fill, palette coloring, camera framing, and
screen-to-tile conversion. It should not require Foundation to construct
OpenFront `GameView`, `FrameData`, units, structures, railroads, nukes,
alliances, HUD, or radial menu state.

## Minimal Shared Inputs For Foundation First Loop

Foundation should only need:

- `width`, `height`.
- `terrainBytes` for an all-grass 256x256 map, plus an agreed byte/color profile.
- `tileState: Uint16Array` where low 12 bits hold owner ID.
- `palette` entry for owner `1` and unowned/default values.
- `camera` state `{ x, y, zoom }`, map fit, resize, and optional external RAF.
- `screenToTile(screenX, screenY)` for click-to-place.
- `setTileState()` or `applyTileDeltas()` after claim-radius mutation.

## Migration Notes

- Batch 1 should not extract passes or alter OpenFront runtime files.
- W2 can wrap the existing OpenFront `WebGLFrameBuilder` path as compatibility.
- W3 can add a Foundation adapter that uploads terrain, palette, and tile state
  without constructing OpenFront `FrameData`.
- W4 can split base-map pass profile from optional OpenFront pass groups once
  OpenFront compatibility tests and Foundation adapter tests are present.
