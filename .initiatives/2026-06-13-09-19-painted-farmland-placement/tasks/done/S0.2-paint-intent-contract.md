**Status**: DOING

**Supports**: D1, D3

## Purpose

Decide whether paint placement sends repeated existing `build_unit` intents or introduces a batched paint intent.

## Scope

- In: Compare first-implementation simplicity, server validation, duplicate suppression, rate limiting, and multiplayer traffic.
- Out: Implementing transport changes unless the decision requires a new intent.

## Touchpoints

- Create: Optional contract note in initiative.
- Modify: `src/client/Transport.ts`, `src/core/Schemas.ts`, and command surfaces only if a batch intent is selected during execution.

## Acceptance Criteria

- [x] The transport approach is chosen and recorded.
- [x] The paint stroke duplicate policy is defined.
- [x] The cancellation semantics for right-click, Escape, and selection changes are defined.

## Test Plan

- `test_paint_intent_contract` - future controller/transport test should assert one intent per accepted tile or one batch per stroke, matching this decision.

## Working Notes

- Planning baseline created.
- Decision: paint placement emits repeated existing `build_unit` intents, one per accepted tile.
- Duplicate policy: a stroke maintains attempted tile refs and does not emit a second intent for the same tile until a new stroke begins.
- Cancellation policy: right-click, Escape, blur, or selecting another build item cancels paint mode and clears brush cursor state.
- Details recorded in `CONTRACT.md`.
