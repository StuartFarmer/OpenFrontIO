# S3.1: Wrap Client Game Creation

**Status**: DONE
**Wave**: W3
**Track**: Client
**Supports**: D3
**Effort**: L
**Dependencies**: S1.1, S1.2

## Purpose

Move current `createClientGame()` ownership behind `OpenFrontClientModule.mount(ctx)` while preserving lobby flow.

The public `joinLobby()` result stays unchanged. This ticket only changes the
game-start handoff so the OpenFront-specific runtime assembly is owned by the
OpenFront client module.

## Scope

- In: Config creation, terrain loading, worker initialization, OpenFront `GameView`, input overlay creation, WebGL view creation, sound manager, frame loop, `ClientGameRunner`.
- Out: Generic client runtime, Foundation client, renderer refactor.
- Boundary: `joinLobby()` may continue to own lobby connection, prestart/join promises, and error modal behavior, but it must delegate game runtime mounting through the OpenFront client module.

## Touchpoints

- Create: `src/games/openfront/client/OpenFrontClientModule.ts`
- Potentially Modify: `src/client/ClientGameRunner.ts`
- No compatibility re-export shims; update imports directly where a function moves.

## Acceptance Criteria

- [x] `joinLobby()` still exposes the same result shape.
- [x] Client game creation delegates through OpenFront module.
- [x] Existing OpenFront start, replay, and single-player paths keep behavior.
- [x] Terrain loading, worker initialization, input overlay, WebGL view, sound, frame loop, and runner construction remain equivalent to the previous `createClientGame()` implementation.
